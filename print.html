Rust Concepts

Introduction

This book is a focused reference for Rust’s core concepts, written for engineers who want depth rather than breadth. Each article follows the same structure: a prose explanation of why the concept exists, a self-contained code example, a list of rules worth memorising, and a concise code-review section that shows the right and wrong way to apply the idea in practice.

The topics are grouped by theme — Ownership, Lifetimes, Iterators, and Traits — so you can read a section end-to-end or jump straight to the article that answers your current question. Every example compiles against stable Rust and is kept short enough to fit in your head.

If you spot an error or want to suggest an improvement, use the “Edit this page” link in the top-right corner of any article.

Ownership & Borrowing

Ownership is the mechanism Rust uses to manage memory without a garbage collector. Every value has exactly one owner at any point in time, and when the owner goes out of scope the value is dropped. Borrowing lets you hand out temporary references — shared (&T) or exclusive (&mut T) — without transferring ownership.

The articles in this section build from the ground up: move semantics first, then the borrow checker’s rules for references.

Move Semantics

In Rust, assigning a heap-allocated value to another variable does not copy it — it moves it. The original variable becomes invalid the moment ownership transfers, and the compiler enforces this at compile time, not at runtime. This design eliminates an entire class of bugs — use-after-free, double-free — without any runtime cost. Types that hold no heap resources (integers, booleans, raw pointers) implement the Copy trait instead and are duplicated cheaply on assignment.

Understanding moves is the key to reading Rust error messages. When the compiler says “value used after move,” it means ownership left the current scope on a previous line and the binding is now empty.

Code

fn print_name(name: String) {
    println!("{name}");
} // `name` is dropped here

fn main() {
    let s = String::from("Mukesh");
    print_name(s);          // ownership moves into the function
    // println!("{s}");     // compile error: value used after move
}

Key Points

  • Assignment of a non-Copy type transfers ownership; the source binding is gone.
  • Passing a value to a function is an assignment — ownership moves into the callee.
  • Returning a value from a function moves it back to the caller.
  • Copy types (i32, bool, char, &T, …) are silently duplicated on assignment.
  • Clone is an explicit, potentially expensive deep copy; Copy is implicit and always cheap.

Code Review

Good

#![allow(unused)]
fn main() {
fn greet(name: &str) {
    println!("Hello, {name}");
}
let s = String::from("Mukesh");
greet(&s);          // borrow — caller keeps ownership
greet(&s);          // can call again
}

Borrowing instead of moving lets the caller reuse s without cloning.

Bad

#![allow(unused)]
fn main() {
fn greet(name: String) {
    println!("Hello, {name}");
}
let s = String::from("Mukesh");
greet(s.clone());   // needless clone just to keep `s` alive
greet(s.clone());
}

Taking String by value forces a heap allocation per call; &str costs nothing extra.

Borrowing

A borrow is a temporary reference to a value that does not transfer ownership. Rust enforces two rules at compile time: you can have any number of shared (&T) references at the same time, or exactly one exclusive (&mut T) reference — never both simultaneously. This rule is the borrow checker’s core invariant, and it guarantees that no two parts of a program can observe a mutation at the same time, eliminating data races in safe Rust entirely.

The lifetime of a reference must not exceed the lifetime of the value it points to. The compiler tracks this automatically in most cases via lifetime elision, and requires explicit annotations only when the relationship is ambiguous.

Code

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let mut v = vec![1, 2, 3];

    let first = &v[0];          // shared borrow
    println!("first = {first}");
    // v.push(4);               // compile error: cannot mutate while borrowed

    v.push(4);                  // shared borrow is no longer live here — OK
    println!("{v:?}");
}

Key Points

  • &T is a shared reference: many can coexist, none can mutate through it.
  • &mut T is an exclusive reference: no other reference of any kind may exist simultaneously.
  • References must always point to valid, live data — dangling references are a compile error.
  • The borrow checker uses Non-Lexical Lifetimes (NLL): a borrow ends at its last use, not at the closing brace.
  • Interior mutability (Cell, RefCell, Mutex) moves the exclusivity check to runtime when compile-time checking is too restrictive.

Code Review

Good

#![allow(unused)]
fn main() {
fn sum(data: &[i32]) -> i32 {
    data.iter().sum()
}
}

Takes a slice reference — works with Vec, arrays, and sub-slices without copying.

Bad

#![allow(unused)]
fn main() {
fn sum(data: Vec<i32>) -> i32 {
    data.iter().sum()
}
}

Consumes the Vec needlessly; the caller loses it after the call and can’t pass a slice.

Lifetimes

A lifetime is the region of code for which a reference is valid. Rust tracks lifetimes at compile time to prove that no reference can outlive the data it points to. In the majority of functions the compiler infers lifetimes automatically through a set of elision rules, so you only write explicit annotations when the compiler cannot figure out the relationship on its own.

The articles here start with explicit annotation syntax and then cover the elision rules that let you omit annotations in the common cases.

Lifetime Annotations

A lifetime annotation does not change how long a value lives — it tells the compiler the relationship between the lifetimes of multiple references. The syntax 'a is just a label; the name carries no inherent meaning. When a function takes two references and returns one, the compiler needs to know which input the output borrows from, because that determines how long the returned reference may be used.

Lifetime parameters are declared in angle brackets after the function name, alongside type parameters. Structs that hold references also require lifetime annotations so the compiler can verify that the struct never outlives the data it borrows.

Code

// The returned reference lives at least as long as both inputs.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

struct Excerpt<'a> {
    text: &'a str,   // struct cannot outlive the string it borrows
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first = novel.split('.').next().unwrap();
    let excerpt = Excerpt { text: first };  // `excerpt` tied to `novel`'s lifetime
    println!("{}", excerpt.text);
}

Key Points

  • 'a on a function means “these references share a lifetime region” — the output lives no longer than the shorter input.
  • Lifetime annotations are checked at the call site, not inside the function body.
  • 'static means the reference is valid for the entire program — string literals are 'static.
  • Structs holding references must annotate every reference field.
  • Generic lifetime bounds (T: 'a) mean “T must outlive ’a”, not “T has lifetime ’a”.

Code Review

Good

#![allow(unused)]
fn main() {
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
}

Elision applies: the output borrows from the single input, no annotation needed.

Bad

#![allow(unused)]
fn main() {
fn first_word<'a, 'b>(s: &'a str, _ctx: &'b str) -> &'a str {
    s.split_whitespace().next().unwrap_or("")
}
}

'b is declared but unused; _ctx is unrelated to the output — misleading and noisy.

Lifetime Elision

Lifetime elision is a set of three inference rules that let the compiler fill in lifetime annotations automatically when the relationship is unambiguous. These rules were added to Rust specifically because the vast majority of real functions either take a single reference and return one derived from it, or take &self and return something tied to self. Writing 'a everywhere in those cases would be mechanical noise with no information value.

The three rules apply in order. First, every reference parameter gets its own distinct lifetime. Second, if there is exactly one input lifetime, it is assigned to all output lifetimes. Third, if one of the input parameters is &self or &mut self, the lifetime of self is assigned to all output lifetimes. If none of these rules fully determine the output lifetime, the compiler requires an explicit annotation.

Code

#![allow(unused)]
fn main() {
// All three functions are identical after elision is applied.

// Written with explicit annotations:
fn get_ref<'a>(x: &'a i32) -> &'a i32 { x }

// Written with elision (rule 2 applies — one input, one output):
fn get_ref(x: &i32) -> &i32 { x }

struct Cache {
    value: String,
}

impl Cache {
    // Rule 3: output borrows from &self
    fn value(&self) -> &str {
        &self.value
    }
}
}

Key Points

  • Rule 1: each & parameter gets its own lifetime label (e.g., 'a, 'b).
  • Rule 2: if exactly one input reference exists, its lifetime flows to every output reference.
  • Rule 3: if &self or &mut self is present, its lifetime flows to every output reference.
  • If the rules produce a unique answer the annotation is elided; otherwise you must write it.
  • Elision is purely a syntactic shortcut — the compiler still checks the full lifetime graph.

Code Review

Good

#![allow(unused)]
fn main() {
impl Config {
    fn name(&self) -> &str { &self.name }
}
}

Rule 3 applies cleanly — no annotation needed, intent is clear.

Bad

#![allow(unused)]
fn main() {
impl Config {
    fn name<'a>(&'a self) -> &'a str { &self.name }
}
}

Explicit 'a here is redundant; elision already handles it and the annotation adds visual clutter.

Iterators

Rust’s iterator system is built on a single trait — Iterator — with one required method, next. Everything else: map, filter, fold, zip, chain, and dozens more combinators, are provided as default methods on that trait. Iterators are lazy: no work happens until a consuming adaptor (collect, for_each, sum, …) or a for loop drives them. This means you can compose a long chain of transformations with no intermediate allocations.

The articles here cover the trait itself and the most useful combinator patterns.

The Iterator Trait

The Iterator trait requires exactly one method: next, which returns Option<Self::Item>. Returning Some(item) advances the iterator; returning None signals exhaustion. Every other method on iterators — map, filter, enumerate, and more than 70 others — is a default implementation built on top of next. When you implement Iterator for your own type you get the full combinator library for free.

A type becomes iterable in a for loop by implementing IntoIterator, which converts the type into an iterator. Vec<T> implements it three ways: consuming (vec), by shared reference (&vec), and by exclusive reference (&mut vec), giving you control over whether the loop takes ownership or borrows.

Code

struct Counter {
    count: u32,
    max: u32,
}

impl Counter {
    fn new(max: u32) -> Self {
        Counter { count: 0, max }
    }
}

impl Iterator for Counter {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.count < self.max {
            self.count += 1;
            Some(self.count)
        } else {
            None
        }
    }
}

fn main() {
    let sum: u32 = Counter::new(5)
        .zip(Counter::new(5).skip(1))
        .map(|(a, b)| a * b)
        .sum();
    println!("{sum}"); // 2*3 + 3*4 + 4*5 + 5*6 … wait, let's just trust the chain
}

Key Points

  • Implement only next; all combinators are inherited default methods.
  • type Item is an associated type — it fixes the element type for a given implementation.
  • Iterators are lazy: combinators return new iterator structs, not computed results.
  • for x in collection desugars to IntoIterator::into_iter(collection) followed by repeated next.
  • iter() borrows, iter_mut() borrows mutably, into_iter() consumes — know which you need.

Code Review

Good

#![allow(unused)]
fn main() {
let evens: Vec<_> = (0..10).filter(|x| x % 2 == 0).collect();
}

Single lazy chain, one allocation at collect.

Bad

#![allow(unused)]
fn main() {
let mut evens = vec![];
for x in 0..10 {
    if x % 2 == 0 { evens.push(x); }
}
}

Manual loop with repeated push — does the same work but misses filter’s intent and may reallocate.

Combinators

Combinators are the default methods on Iterator that transform or consume a sequence without requiring a manual loop. They fall into two groups: adapters return a new iterator (lazy, no work done yet), and consumers drive the iterator to completion and produce a final value. Adapters can be chained freely in any order; the work only happens when a consumer is called at the end of the chain.

The most common adapters are map (transform each element), filter (keep matching elements), flat_map (transform then flatten), take / skip (slice the sequence), and enumerate (pair each element with its index). The most common consumers are collect, sum, fold, any, all, and for_each. Knowing which is which matters because calling an adapter without a consumer produces a warning: you built an iterator that nothing ever polls.

Code

fn word_lengths(text: &str) -> Vec<(usize, &str)> {
    text.split_whitespace()
        .filter(|w| w.len() > 3)          // adapter: skip short words
        .enumerate()                       // adapter: attach index
        .map(|(i, w)| (i + 1, w))         // adapter: 1-based index
        .take(5)                           // adapter: cap at 5 results
        .collect()                         // consumer: materialise into Vec
}

fn main() {
    let results = word_lengths("the quick brown fox jumps over the lazy dog");
    for (n, word) in &results {
        println!("{n}: {word}");
    }
}

Key Points

  • Adapters are lazy — no iteration happens until a consumer is reached.
  • fold(init, |acc, x| ...) is the generalisation that most other consumers are built on.
  • flat_map is map + flatten; use it when each element produces a sequence.
  • chain concatenates two iterators without allocating a new collection.
  • peekable() wraps an iterator so you can inspect the next element without consuming it.

Code Review

Good

#![allow(unused)]
fn main() {
let total: i32 = scores.iter().filter(|&&s| s > 0).sum();
}

One lazy pass, no temporary collection.

Bad

#![allow(unused)]
fn main() {
let positive: Vec<_> = scores.iter().filter(|&&s| s > 0).collect();
let total: i32 = positive.iter().sum();
}

Allocates positive only to immediately sum it — split into two passes for no reason.

Traits & Generics

A trait is Rust’s mechanism for defining shared behaviour. It is similar to an interface in other languages, but stricter: you cannot add methods to a trait after the fact, and the compiler resolves which implementation to call at compile time by default (static dispatch). Generics let you write functions and types that work over any type satisfying a trait bound, with the compiler generating specialised code for each concrete type used.

The articles here cover the two dispatch strategies — static via generics and dynamic via trait objects — and the mechanics of writing generic code with bounds.

Trait Objects

A trait object — written dyn Trait — is a fat pointer that pairs a data pointer with a vtable at runtime. It enables dynamic dispatch: the method to call is looked up in the vtable at runtime rather than resolved at compile time. This means you can store values of different concrete types behind a single Box<dyn Trait> or &dyn Trait, which is impossible with generics (where the type must be known at compile time).

The cost of dynamic dispatch is a pointer indirection per method call and the loss of monomorphisation optimisations. For most use cases the cost is negligible, but it matters in tight inner loops. Trait objects also impose an object safety requirement: the trait cannot have methods that return Self or use generic type parameters, because the vtable would then need to encode an unbounded set of implementations.

Code

trait Draw {
    fn draw(&self);
}

struct Circle;
struct Square;

impl Draw for Circle {
    fn draw(&self) { println!("drawing circle"); }
}

impl Draw for Square {
    fn draw(&self) { println!("drawing square"); }
}

fn render_all(shapes: &[Box<dyn Draw>]) {
    for shape in shapes {
        shape.draw();   // vtable lookup at runtime
    }
}

fn main() {
    let shapes: Vec<Box<dyn Draw>> = vec![
        Box::new(Circle),
        Box::new(Square),
    ];
    render_all(&shapes);
}

Key Points

  • dyn Trait is a fat pointer: 16 bytes (data pointer + vtable pointer) on 64-bit platforms.
  • Use trait objects when the set of concrete types is not known at compile time.
  • A trait is object-safe if no method uses Self by value or has generic type parameters.
  • Box<dyn Trait> owns the value; &dyn Trait borrows it.
  • dyn Trait + Send + Sync adds auto-trait bounds for use across threads.

Code Review

Good

#![allow(unused)]
fn main() {
fn notify(sender: &dyn Notify) {
    sender.send("hello");
}
}

&dyn Notify avoids boxing when ownership isn’t needed — cheaper and more flexible.

Bad

#![allow(unused)]
fn main() {
fn notify(sender: Box<dyn Notify>) {
    sender.send("hello");
}
}

Box forces a heap allocation at the call site even though the function only needs to borrow.

Generics

Generics let you write a function or type once and have the compiler specialise it for every concrete type it is called with. This is monomorphisation: at compile time, Rust generates a separate copy of the code for each distinct type argument. The result is code that runs as fast as if you had written a dedicated version by hand, with zero runtime overhead — unlike dynamic dispatch via trait objects.

Trait bounds (T: Display, T: Clone + Debug) constrain the generic parameter so the compiler knows which methods are available inside the function. The where clause is an alternative syntax for the same bounds, preferred when the bound list grows long enough to obscure the function signature. impl Trait in an argument position is syntactic sugar for a generic parameter with a single bound; in a return position it means “some concrete type implementing this trait” (useful for returning closures or iterators without naming the type).

Code

#![allow(unused)]
fn main() {
use std::fmt::Display;

fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn print_pair<T, U>(a: T, b: U)
where
    T: Display,
    U: Display,
{
    println!("{a} and {b}");
}

fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    move |y| x + y
}
}

Key Points

  • Monomorphisation generates one concrete function per type argument — no runtime overhead.
  • Bounds written as T: TraitA + TraitB require the type to implement both traits.
  • where clauses improve readability when multiple type parameters each have several bounds.
  • impl Trait in argument position is sugar for an anonymous generic; in return position it hides the concrete type.
  • Blanket implementations (impl<T: Display> MyTrait for T) apply a trait to any type satisfying a bound.

Code Review

Good

#![allow(unused)]
fn main() {
fn print<T: Display>(value: &T) {
    println!("{value}");
}
}

Generic over Display — works with any printable type, no boxing, zero overhead.

Bad

#![allow(unused)]
fn main() {
fn print(value: &dyn Display) {
    println!("{value}");
}
}

&dyn Display adds a vtable indirection for a function that is always called with a known type — use generics instead.
